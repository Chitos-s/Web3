# Корпоративный портал заявок

Лабораторная работа по Django на тему `Middleware и расширенная логика Django`.

Проект реализует внутренний портал заявок, где сотрудники создают обращения к корпоративным сервисам, прикладывают файлы, меняют статус, оставляют комментарии. Система ведет аудит действий, отслеживает изменения, применяет ограничения по частоте запросов через middleware.

## Что реализовано

- роли пользователей: `user`, `moderator`, `admin`;
- модели:
  - `ServiceRequest` - заявка;
  - `Comment` - комментарий;
  - `ChangeHistory` - история изменений;
  - `UserSettings` - настройки пользователя;
  - `AuditLog` - журнал аудита;
  - `UserProfile` - профиль с ролью;
- HTML-интерфейс:
  - список заявок с фильтрами;
  - карточка заявки;
  - создание заявки;
  - редактирование заявки;
  - панель модератора;
  - страница пользовательских настроек;
- REST API для основных сущностей;
- middleware:
  - генерация и проброс `request id`;
  - audit log по запросам;
  - rate limit для отдельных endpoint;
  - автоопределение пользователя по заголовку `X-Portal-User`.

## Стек

- Python 3.13
- Django 6
- Django REST Framework
- SQLite

## Запуск проекта

```bash
python manage.py migrate
python manage.py seed_portal
python manage.py runserver
```

После запуска сайт будет доступен по адресу:

```text
http://127.0.0.1:8000/
```

## Демо-пользователи

Команда `seed_portal` создает 3 аккаунта:

- `employee / portal12345` - обычный пользователь
- `moderator / portal12345` - модератор
- `adminportal / portal12345` - администратор

## Основные страницы

- `/` - список заявок
- `/requests/create/` - создание заявки
- `/requests/<id>/` - карточка заявки
- `/requests/<id>/edit/` - редактирование заявки
- `/moderator/` - панель модератора
- `/settings/` - настройки пользователя
- `/accounts/login/` - вход

## REST API

Базовый префикс:

```text
/api/
```

Доступные ресурсы:

- `/api/requests/`
- `/api/comments/`
- `/api/history/`
- `/api/settings/`
- `/api/audit-log/`

Дополнительное действие для заявок:

- `POST /api/requests/<id>/change_status/`

## Что проверять после запуска

### 1. Проверка ролей

1. Войти как `employee`.
2. Убедиться, что доступны только свои заявки.
3. Попробовать открыть чужую заявку напрямую по URL: должен быть запрет.
4. Войти как `moderator`.
5. Убедиться, что видны все заявки и доступна панель модератора.
6. Войти как `adminportal`.
7. Убедиться, что доступны все действия без ограничений по рабочему времени.

### 2. Проверка заявок

1. Создать новую заявку.
2. Заполнить поля `title`, `description`, `service_type`, `priority`.
3. Прикрепить файл.
4. Открыть карточку заявки и проверить отображение вложения.
5. Отредактировать заявку.
6. Проверить, что изменения появились в блоке истории.

### 3. Проверка комментариев

1. Добавить комментарий в карточке заявки.
2. Для модератора добавить внутренний комментарий.
3. Проверить, что обычный пользователь не видит внутренние комментарии.

### 4. Проверка middleware

#### `Request ID`

Открыть любую страницу или endpoint API и проверить заголовок ответа:

- `X-Request-ID`
- `X-Response-Time-ms`

Также можно передать свой заголовок:

```text
X-Request-ID: demo-123
```

#### `Auto user detection`

Можно отправить запрос без сессии, но с заголовком:

```text
X-Portal-User: employee
```

После этого в `AuditLog` должен сохраниться пользователь `employee`.

#### `Audit log`

После любых переходов по сайту или API проверить, что в таблице `AuditLog` сохраняются:

- пользователь;
- IP;
- user agent;
- метод;
- путь;
- статус ответа;
- request id.

#### `Rate limit`

Несколько раз быстро вызвать один и тот же ограниченный endpoint:

- `/api/requests/`
- `/api/comments/`
- `/requests/create/`

После превышения лимита должен вернуться статус `429`.
